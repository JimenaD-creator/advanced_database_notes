# Session – 2026-04-14

## Topics covered
- **Indexes:** Understanding how an index stores the indexed column values alongside a ROWID to provide a direct path to the data.
- **Full Table Scan (FTS):** Identifying when the engine chooses to read every block in a table sequentially rather than using a lookup.
- **SQL Engine (CBO):** Learning how the Cost-Based Optimizer calculates the most efficient execution plan by comparing the cost of I/O for different access paths.
- **B-Tree Structure:** Exploring the balanced tree hierarchy (Root, Branch, Leaf) that allows the engine to find data in a logarithmic number of steps.
- **Composite Indexes:** Analyzing how multiple columns are concatenated in a single index and how this affects search efficiency.

## What I understood
- I learned that an index is only efficient when it filters a small percentage of the total rows. If a column has low cardinality (few unique values), the overhead of reading the index plus the table is higher than simply performing a Full Table Scan.
- I understood that the optimizer often ignores indexes if the query requests a large portion of the table. Reading the whole table sequentially is often faster than jumping back and forth between the index and the table data for thousands of records.
- I realized that applying functions like TRUNC() or TO_CHAR() to a column in the WHERE clause prevents the engine from using a standard index. The column must remain in its original state for the index to be recognized.
- In a composite index on (Column_A, Column_B), the order matters. The engine can efficiently use the index if the leading column (Column_A) is part of the search criteria, but it cannot easily navigate the tree if only the second column is provided.

## What is still confusing
